# sldr studio is an API-first web satellite; Oqto is a second client

sldr needs an interactive authoring surface — managing the slide library and building decks, editing flavors, and editing layouts — that is usable from a phone over a private network and embeddable inside Oqto, without compromising the lean, node-free core. The earlier integration plan (trx-3f4w) predates sldr's own renderer and assumed a slidev process manager with `v-drag` templates; that approach is obsolete now that the deterministic Rust compiler renders the real deck.

We resolve it the same way the project already resolves convenience layers: **studio is a [[satellite]], and the HTTP API is the product — the UI is just a client.**

- **Studio is a satellite** (per ADR-0001 and the satellite definition in CONTEXT.md): disposable, writes only canonical files (`slides/*.md`, `flavors/*/flavor.toml`+`.css`, `layouts/*.html`, `playlists/*.toml`), and introduces no new format or state store. Deleting it loses no data and no capability.
- **Mechanical, not curation.** Studio does browse / preview / create / arrange / build. Judgment-heavy librarian work (dedupe, enrichment, quality grading, supersession) stays out — that belongs to agents and the separate curation product. This keeps the boundary with the curation platform clean.
- **API-first.** `sldr-server` (axum) is extended into the complete studio API — the existing `slides` / `playlists` / `flavors` / `build` / `preview` endpoints plus `layouts` CRUD and zone parse/emit. That API is the single contract and the integration surface. The standalone studio frontend is one client; Oqto is another; agents are a third. Logic lives in the core and the API, never in a UI.
- **Web-served, network-reachable, hosted by Oqto.** sldr is already a registered Oqto app (`apps/sldr`); studio is the build-out of that app, not a new frontend. Oqto runs on the server and is reached over Tailscale from a phone or laptop, so "manage slides from my phone" is satisfied by Oqto hosting the studio app — no separate shell to build. Auth, theming, i18n, and data-fetching are Oqto's: the studio calls the sldr API through Oqto's `authFetch` (Bearer token in `localStorage`, the "light token") and React Query, via the `/api` proxy. The bearer token is sufficient for a Tailscale-only deployment, explicitly not hardened for public exposure (a real login is future work).
- **Frontend is the Oqto app, reusing Oqto's design system.** React 19 + Vite + Tailwind 4, consuming the vendored byteowlz design system (`vendor/design-system`, shadcn/Radix, synced across repos by `byt design-system sync` from the shared `design-system` repo). Studio reuses Oqto's `@/components/ui/*`, `cn()`, and theme tokens rather than restyling. A standalone `sldr studio` serve remains *possible* later against the same API, but is not a deliverable — building it would mean re-implementing Oqto's shell (auth, nav, theme) for no current need.
- **The core invariant is preserved exactly where it matters.** The `sldr` CLI and every deck artifact remain pure-Rust and node-free. Node is confined to the studio frontend project — a separately built satellite, never invoked by `cargo build` of the core.
- **Three sections.** (1) Slide management + deck building — mobile-first, since that is the phone use case. (2) Flavor editor — rebuilt on the current token model (`type_scale`, `density`, per-role sizes, `chrome_layouts`, `.sldr-chrome` hooks); this replaces and retires the `sldr flavor` command. (3) Layout editor — HTML + scoped CSS editing with a visual PPTX-zone editor that emits the `<!-- sldr:zone … -->` directives.

## Considered Options

- **Tauri desktop app** (rejected as primary): a desktop binary does not serve a phone, which is the driving use case; it also would not mount inside Oqto. Tauri could later *wrap* the same web app as an optional desktop shell, but it is not the thing.
- **In-binary, no-node frontend** (vanilla / vendored, or Rust→WASM) (rejected): it forecloses both Oqto integration and reuse of the shared design system, and a widget-heavy editor (code editing, pickers, drag-to-position zones) devolves into JS-interop glue under WASM. The "no node" rule protects *shipped artifacts*, not the dev tooling of a disposable satellite.
- **A standalone studio web app with its own shell** (rejected as primary): it re-implements auth, nav, theming, and i18n that Oqto already provides and already hosts an `sldr` app for. API-first keeps it possible later, but it is wasted work now.
- **API-first satellite, frontend is the Oqto app** (chosen): one HTTP contract; the studio is the built-out Oqto `sldr` app reusing Oqto's shell and design system; the core stays node-free; agents and a future standalone client consume the same API for free.

## Consequences

- `sldr-server` grows from a partial API into the full studio API: `layouts` CRUD and zone parse/emit are added alongside the existing `slides` / `playlists` / `flavors` / `build` / `preview`. Backend operations are plain functions so the API never owns logic the CLI cannot also reach.
- The existing Oqto `sldr` app (`apps/sldr` / `features/sldr/`) is built out into the three studio sections, reusing Oqto's design system, auth, React Query, and theming; live preview is always an iframe of the real renderer output, never a reimplementation.
- `sldr flavor` (the `flavor_builder` satellite) is removed; its capability moves into the studio flavor editor, rebuilt on the current token surface.
- Auth is a bearer token bound to a Tailscale-only deployment; public exposure is out of scope until a real auth story exists.
- The prior Octo-integration epic (trx-3f4w) is refreshed off slidev onto the native renderer; its completed pieces (the `sldr-server` crate, route mounting, the SlideLibrary component) carry forward.
- Studio writes only canonical files and is fully disposable, so the curation product and any other client can be built against the same API without coordination.
