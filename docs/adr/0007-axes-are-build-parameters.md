# Axes are build parameters; the library carries its assets

**Library self-sufficiency.** All assets — slides, layouts, flavors, playlists, media — live under one library root (`~/sldr/` by default), making the library a self-sufficient, git-trackable tree: clone + build works. The config dir holds configuration, not assets; the old global asset dirs survive only as optional extra search paths. Resolution order is deterministic: library → configured extra paths → built-ins embedded in the binary. A reference that resolves nowhere fails the build loudly, naming the missing layout/flavor and the searched paths — never a silent substitute (a deck that builds wrong is worse than one that doesn't build; the precise error is all an agent needs).

**Flavor and language are axes, not properties of the playlist.** A playlist is pure content selection — which slides, what order; it *may* carry a default flavor/language set as a suggestion, but a playlist without one is complete. The conundrum "where do flavors get declared?" dissolves into three layers:

1. **Playlist** (library-side): content; optional axis defaults.
2. **Build invocation**: resolves the axes (`--flavor a,b,c` = the embedded set, `--lang de,en`) with precedence CLI > playlist default > config default. Style meets content exactly once, explicitly.
3. **Artifact**: records what was resolved. The `.sldr` bundle carries a **manifest** — the resolved build parameters beside the sources — refining ADR-0006: the manifest pins the axes, the bundled playlist stays clean, so the bundle rebuilds identically *and* remains restylable. Bundles ship the transitive closure only (referenced slides, their layouts, the resolved flavors, their media), never the whole library.

**Frontend switching falls out of the existing guarantees.** Flavor switching needs no recompile: flavors touch only the style layer (the confined-diff invariant), so N embedded `<style data-flavor>` blocks toggle by pure CSS — the presenter's existing mechanism. Language is a *content* axis, so it embeds as parallel content blocks toggled by attribute (the dark-mode/multi-flavor pattern); text is cheap and media is shared, so the axes stay additive, never multiplicative. Recompile-on-switch is the dev-server path only.

**Languages live inside the slide file.** A `talk_de.md` fork is the translation equivalent of `-v2` copies — structure, media, and layout drift immediately. All languages of a slide share one file: same frontmatter, layout, media, and step structure; only prose varies, and staleness is visible in the same diff. A slide missing a requested language falls back to the deck's default language with a loud build warning — fallback rather than failure because a one-slide gap is visible and survivable on stage, but it must never happen silently. Translation itself is agent work, in-file.
